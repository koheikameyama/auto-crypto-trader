## 2. なぜ ¥100,000 か

Phase 2.1（¥30,000）の trade 規模 ~¥1,500〜3,000 では:

- 整数 JPY fee で bps が振れやすい（¥1〜¥2 単位）
- minimum lot 0.0001 BTC (¥1,275) ギリギリの境界で skip が発生しやすい
- slippage / fee の統計的に意味のある実測が困難

¥100,000 規模では:

- 1 rebalance あたり trade 規模 ~¥6,000〜10,000 → bps が安定
- minimum lot からの margin が拡大、target distribution に近い rebalance 頻度が観測可能
- Round 12 で観測した「maker fill 率 50%、effective fee 3.93 bps」が ¥100k 規模でも再現するかを検証

## 3. 観測指標

### 3.1 Phase 2.2 → 2.3 移行条件

| 指標 | 目標 | 計測方法 |
|---|---|---|
| 発注成功率 | ≥ 95% | OrderLog status=filled / total |
| Maker LIMIT fill 率 | ≥ 30%（Round 12 W300 で 50%） | OrderLog の orderType=LIMIT で status=filled の比率 |
| Effective fee（fill 率込み） | ≤ +5 bps 平均 | `feeJpy / (execUnits * execPrice)` の平均 |
| Slippage | ≤ 30 bps 平均（MARKET fallback 時） | OrderLog.slippageBps の MARKET 分の平均 |
| Virtual vs Actual equity 差 | ≤ 1.5%（Phase 2.1 は 1%） | compare-dashboard で日次確認 |
| Kill switch trigger | 0 回 | OrderLog で status=failed の連続日数 |
| 手動介入 | 0 回 | 観察期間中の手動 rebalance / 設定変更なし |

### 3.2 Round 12 仮説の本番検証

Round 12 の小ロット（0.0001 BTC）実験では W300-inside で:
- Fill 率: 50% (2/4)
- Effective fee: 3.93 bps

¥100k 規模の trade（~0.0005〜0.0008 BTC）で同等の fill 率 / fee が出るか、サンプル数を稼いで確認。

## 4. オペレーション

### 4.1 開始手順（2026-05-12 完了済）

- [x] GMO 口座に ¥100,000 入金（ユーザー対応）
- [x] `EXECUTION_ENABLED=true` 維持（Phase 2.1 から継続）
- [x] `EXECUTION_ASSETS=BTC` 維持（[forbidden.md #6](../claude/forbidden.md) に従い ETH は追加しない）
- [x] cron-job.org daily run 10:05 JST（変更なし）

### 4.2 日次確認

- Slack 通知で actual rebalance の有無 / fee / slippage を目視
- 週次（毎週月曜）に `compare-dashboard.ts --asset=BTC --days=14` で virtual vs actual の equity 比較

### 4.3 異常時の対応

- 連続 2 日の発注失敗 → `gh secret set EXECUTION_ENABLED <<< 'false'` で actual のみ停止（virtual は継続）
- Equity が ¥70,000 未満（30% DD）→ kill switch が自動 trigger（[execution-adapter.ts](../../src/live/execution-adapter.ts) DEFAULT_KILL_SWITCH 参照）
- Slippage > 50 bps が単発でも発生 → 原因調査タスクを Linear で起票

## 5. 完了判定（2026-06-12 目処）

1. 上記 3.1 の指標を 1 ヶ月分の OrderLog / ActualPortfolioState から集計
2. PASS なら Phase 2.3 Seed（¥1,000,000）を別 plan として起票
3. FAIL の場合、原因に応じて:
   - Fill 率不足 → Round 12.5（slippage 上限 check 等の execution 改善）
   - Equity 乖離大 → signal / DB データ品質の調査
   - Kill switch trigger → API key / 市場異常の調査

## 6. リスク

| リスク | 影響 | Mitigation |
|---|---|---|
| Trade 規模が ¥6,000+ になり slippage が小ロット実験より悪化 | Effective fee が想定外 | 日次 Slack で目視、悪化が継続するなら Round 12.5 |
| BTC 価格急変で 1 ヶ月の DD が想定超 | Phase 2.3 移行が遅延 | kill switch が自動停止、virtual も継続観測 |
| GMO API 仕様変更 / 認証エラー | 発注失敗 | OrderLog で連続失敗を検知 → 手動対応 |
| Round 12 の maker wait 300s が実 trade では fill 率低下 | Effective fee 悪化 | サンプル数を稼いで判定、PASS しなければ wait 調整も検討 |
