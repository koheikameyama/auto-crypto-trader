# Phase 2 増額判断条件（¥100,000 → ¥300,000 → ¥1,000,000）

**作成日:** 2026-07-28
**Linear:** [KOH-590](https://linear.app/koheikameyama/issue/KOH-590)
**スコープ:** ドキュメントのみ。コード・パラメータ変更なし。

---

## 1. なぜ今これを書くか

Phase 2.2 は 2026-07-11 に PASS 判定を受けて ¥100,000 本運用化した（[2026-05-12-phase-2-2-small.md](2026-05-12-phase-2-2-small.md)）。
以後の増額は「利益積み増しで段階的に検討」とだけ決まっており、**判定基準が未定義**。

基準を決めずに運用を続けると、含み損の局面では判断を先送りし、含み益の局面では
根拠なく増額する、という一番まずいパターンに落ちる。増額は不可逆ではないが
（減額はできる）、規模が上がるほど執行の前提（ロット、slippage、板の厚み）が
変わるため、**事前に条件を固定しておく**。

## 2. 現時点のエビデンス（2026-07-28）

### 2.1 下落局面（2026-05-20 満額 〜 2026-07-28）

| 項目 | 値 |
|---|---|
| 総 equity | ¥98,572 → ¥95,613 = **-3.0%** |
| BTC/JPY | ¥12,208,193 → ¥10,381,011 = **-15.0%** |
| **BH 対比** | **+12pp** |
| 平均 actual position | BTC 0.298 / ETH 0.316 |

→ **戦略の防御機能はライブで実証済み。** backtest で期待した regime sizing の
downside 抑制が再現された。

### 2.2 上昇局面（2026-07 単月）

| 項目 | 値 |
|---|---|
| 戦略 TWR | **+2.98%** |
| 等加重 BH（BTC/ETH、JPY 建て） | **+9.18%** |
| **アルファ** | **-6.19%** |
| 捕捉率（戦略 ÷ BH） | **32%** |

→ **上昇局面での取り逃しもライブで確認された。** これは Scheme E の既知の性質
（backtest 上も BH 対比で upside を削る）であり不具合ではないが、増額の判断では
「守れる」だけでなく「どれだけ取り逃すか」を明示的に評価する必要がある。

|---|---|---|---|
| 発注失敗 | 0 件 | 0 | ✅ |

| Effective fee | +1.46bps | ≤+5bps | ✅ |
| Slippage | avg 1.3 / max 3.6bps | ≤30bps | ✅ |

## 3. 増額の段階

| 段階 | 規模 | 最短判定時期 | 前段からの観察期間 |
|---|---|---|---|
| 現在 | ¥100,000 | — | — |
| **S1** | **¥300,000** | **2026-11-12 以降** | Phase 2.2 開始から 6 ヶ月 |
| S2 | ¥1,000,000 | S1 実行から 6 ヶ月以降 | 6 ヶ月 |

一度に 3 倍を超えて増額しない。ロット・板の厚み・slippage の前提が
非連続に変わるのを避けるため。

## 4. S1（¥100,000 → ¥300,000）の判定条件

### 4.1 必須ゲート（すべて満たすこと）

| # | ゲート | 条件 | 計測 |
|---|---|---|---|
| **G1** | 観察期間 | Phase 2.2 開始（2026-05-12）から **6 ヶ月以上** | カレンダー |
| **G2** | 執行健全性 | 直近 **3 ヶ月連続**で、月次サマリの全項目が基準内（発注失敗 0 / fill 率 ≥30% / effective fee ≤+5bps / slippage avg ≤30bps） | `monthly-summary.ts` |
| **G3** | 下落局面の防御 | BTC/JPY が **-10% 以上**下げた局面を 1 回以上通過し、その期間の戦略リターンが **BH の 1/2 以下の下落**に収まっている | 月次サマリ / 手動集計 |
| **G4** | 上昇局面の捕捉 | BTC/JPY が **+15% 以上**上げた局面を 1 回以上通過し、その期間の戦略の**捕捉率 ≥30%** | 同上 |
| **G5** | Virtual 追随 | 月次の virtual vs actual 乖離が **3 ヶ月連続で ±3pp 以内** | `monthly-summary.ts` |
| **G6** | Kill switch | 観察期間中の**実発火 0 回**（データ品質バグ起因の誤発火は、修正済みかつ原因が特定されていれば除外） | `ActualPortfolioState.skipReason` |
| **G7** | 手動介入 | 戦略パラメータの手動変更 0 回 | git log / 運用記録 |

### 4.2 現時点の充足状況（2026-07-28）

| ゲート | 状況 |
|---|---|
| G1 | ❌ 未達（2026-11-12 以降） |
| G2 | 🟡 2026-07 は基準内。あと 2 ヶ月分の実績が必要 |
| G3 | ✅ **達成**（BTC/JPY -15.0% に対し戦略 -3.0%、1/5） |
| G4 | 🟡 未達（2026-07 は BH +9.5% で +15% 基準に届かず。捕捉率 32% は参考値として基準を満たす水準） |
| G5 | 🟡 2026-07 は BTC +1.99pp / ETH -3.05pp。ETH は起点日の違いによる見かけ上の差 |
| G6 | 🟡 -52.6% の kill switch 記録 4 件は 2026-07-11 修正済のデータ品質バグ起因（commit `0a5a521` / `be253b4`）。以後 0 件 |
| G7 | ✅ 達成 |

**→ 現時点では S1 の条件を満たさない。最短で 2026-11-12 に再評価。**

### 4.3 望ましいが必須としない条件

- 運用開始来 TWR がプラス、または等加重 BH を上回る
  - **必須にしない理由:** Scheme E は BH 超過リターンを狙う戦略ではなく、
    risk-adjusted return（Sharpe / MAR）を改善する戦略。BH が大きく上げる局面で
    絶対リターンが劣後するのは設計通りであり、これを必須ゲートにすると
    「ブル相場では永久に増額できない」という誤った制約になる。

## 5. 減額・停止条件（増額と対で先に決める）

| # | トリガー | アクション |
|---|---|---|
| **D1** | 運用開始来 TWR ≤ **-20%** | `EXECUTION_ENABLED=false` で actual 停止（virtual は継続）、原因調査 |
| **D2** | 3 ヶ月連続で BH に劣後 **かつ** 期間 TWR がマイナス | 増額凍結。signal / データ品質の調査タスクを起票 |
| **D3** | Kill switch の**実発火**（データバグ以外） | 増額凍結。発火要因を findings に記録するまで解除しない |
| **D4** | 執行健全性が 2 ヶ月連続で基準外 | 増額凍結。Round 12.5（execution 改善）を起票 |
| **D5** | GMO API 仕様変更 / 認証エラーが 2 日連続 | actual 停止、手動対応 |

D1〜D5 に該当した場合、**解除後あらためて G1 の観察期間をリセットして数え直す**。

---

## 6. 運用

- 判定は**月次サマリ**（[monthly-summary.yml](../../.github/workflows/monthly-summary.yml)、毎月 1 日 10:30 JST）の出力をもとに行う
- G3 / G4 の局面判定は自動化しない。四半期に一度、人が価格チャートを見て
  「該当する局面があったか」を判断する
- 増額を実行する場合の手順:
  1. GMO 口座に追加入金
  2. `npx tsx scripts/record-deposit.ts` で `DepositEvent` に記録（TWR の連続性を保つため必須）
  3. 増額後 1 週間は日次 Slack を目視で確認（ロット拡大による slippage 変化の検知）
